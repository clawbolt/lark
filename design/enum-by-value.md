# 设计：不递归的枚举按值存放

状态：两步都已实现（枚举见第 7 节，T? 见第 8 节），规则已并进 DESIGN.md 第 19 节。

## 1 为什么做

`make bench` 里，`tokens`（不递归的小枚举）267ms，用结构体做同样的事的 `tokflat` 40ms，**差 6.7 倍**。原因是现在每个枚举值都单独分配在堆上：

- 构造一次 `Num(i)` 就是一次 `malloc`，释放一次就是一次 `free`；
- 列表 `[Tok]` 存的是指针，遍历时每个元素都要多跳一次，缓存也不连续。

`T?` 现在同样是“指向堆上 T 的指针”，所以 `m.get(k) ?? 0` 这种每次查找都会分配一次。这是同一个问题，放在第二步解决（第 8 节）。

## 2 对语言没有可见的变化

这是纯实现上的改动：类型规则、所有权规则、`match` 的写法和结果都不变，现有程序不用改。变的只有速度和值的大小。

## 3 哪些枚举按值存放

规则：**枚举按值存放，除非它通过“按值包含”关系包含它自己。**

“按值包含”指：结构体的字段、元组的元素、按值存放的枚举的变体字段。下面这些本来就在堆上，**切断**包含关系：列表 `[T]`、`T?`（第一步里）、`str`、`shared T`、`dyn I`、`Fn`、`Chan`。

| 例子 | 结果 |
|---|---|
| `enum Tok { Num(int), Plus, Times }` | 按值 |
| `enum Shape { Circle(r: int), Rect(w: int, h: int) }` | 按值 |
| `enum Json { …, Arr([Json]), Obj(…) }` | 按值：自己只出现在列表里 |
| `enum Ex { Lit(int), Add(Ex, Ex) }` | 在堆上（同现在） |
| `enum List[T] { Cons(T, List[T]), Nil }` | 在堆上 |
| `type A { b: B }` 加 `enum B { X(A), Y }` | 在堆上：B → A → B 成环 |

- 做法：代码生成前，在所有结构体、元组、枚举（泛型按实例）上建“按值包含”的图，**在环上的枚举**在堆上，其余按值。环上的结构体本来就会报“按值包含了自己”，现在规则不变：结构体经过一个在堆上的枚举成环是合法的。
- 不设大小上限：变体字段很多的枚举也按值存放（和 Rust 一样）。这让规则只有一条；如果以后测出大枚举的复制太慢，再考虑加上限。

## 4 内存布局

按值存放的枚举：

```c
struct E_Tok { int32_t tag; union { char _empty; struct { int64_t f__0; } v1; } u; };
```

- **tag 0 留给“已移走 / 空”**，变体的 tag 从 1 开始。这样“移走 = 按位清零”的现有做法照旧：清零后 tag 为 0，析构遇到 tag 0 什么都不做。这和结构体被移走后按位清零是同一个机制，不需要运行时的额外标记。
- 在堆上的枚举不变：仍是指向 `{ tag, union }` 的指针，NULL 表示已移走。为了让两种代码生成走同一条路，堆上的枚举也改成 tag 从 1 开始。（已实现：判断放在哪里在类型检查结束时算出，存在 `Ctx.tboxed`；生成代码用 `eacc` 统一访问 tag 和字段。）

## 5 各操作怎么生成

| 操作 | 按值 | 在堆上（不变） |
|---|---|---|
| 构造 `V(a, b)` | 返回 `{ .tag = k, .u.vk = { a, b } }` | `lk_alloc` 再填字段 |
| 析构 | 按 tag 释放字段，tag 置 0 | 同左，再 `free` |
| 复制 `.copy()` | 按 tag 逐字段复制 | 分配新的再逐字段复制 |
| `==`、`show`、`hash` | 通过指针 `&x` 访问，和堆上的一样 | 不变 |
| 借用 `match x` | 取一次 `E* e = &x`，之后和堆上的一样用 `e->u.vk.f`；绑定的名字指向 `x` 内部 | 不变 |
| `match take x` | 字段按位移给绑定的名字，`x` 的 tag 置 0，不 `free` | 移走字段后 `free` |
| 有自定义 `drop` | tag 不为 0 时先调用 `drop`，再释放字段 | 不变 |
| 放进列表、`T?`、`Chan` | 按值（元素大小就是枚举的大小） | 存指针 |

- 实现上，把代码生成里“枚举就是指针”的地方集中成两个辅助函数：取得指向值的指针（按值的是 `&x`，在堆上的是 `x`），以及“是否为空”（`x.tag == 0` 或 `x == NULL`）。其余代码都改成调用它们。
- 函数参数：只读参数和 `inout` 参数现在对非复制类型已经是传指针，所以大的枚举传参不会整个复制。
- `dyn`、`Chan` 按元素的字节数存放，本来就不关心元素多大。

## 6 预期效果

- `tokens` 降到接近 `tokflat`（40～60ms）。
- 编译器自己受益不大：它的 token 是结构体，`ExprKind`、`StmtKind`、`Pat` 都是递归的，仍在堆上。所以“lark1 编译自己”预计基本不变。主要受益的是用户程序里状态、消息、结果这类小枚举。
- 第二步做了 `T?` 之后，`std/map` 的 `get`、迭代器的 `next` 每次都少一次分配，maps 一项应该明显变快。

## 7 第一轮：枚举（实现）

1. `cg_types.lark`：建按值包含的图，找出环上的枚举，记一张“在堆上的枚举”表；按两种布局生成类型、构造、析构、复制、比较、插值。
2. `cg_expr.lark` / `cg_stmt.lark`：`match`、`match take`、移动、`T?` 和列表里的枚举都改用第 5 节的两个辅助函数。
3. 测试：现有的示例和用例必须全部通过，输出不变；新加一个示例，覆盖按值的枚举放在结构体、元组、列表、`T?`、Map 的值里，`match take`、自定义 `drop`、在线程间 `send`，以及一个经过结构体成环、因此在堆上的枚举。
4. `make bench` 前后各跑一次；`make asan` 的思路也用在新例子上（`-fsanitize=address`），确认没有重复释放和泄漏。

## 8 第二轮：T? 按值

- `T?` 变成 `{ bool some; T v; }`（`T` 是按值的类型时），`None` 是 `some == false`。
- 环的规则一样：`T?` 和其它按值包含关系一起参与成环判断。`type Node { next: Node? }` 这种通过 `T?` 的自引用要继续在堆上，所以这一类 `T?` 保持指针。
- 这一步改的地方比枚举多（`?`、`??`、自动包成 `Some`、`std/map` 里的槽位都会用到），单独一轮做，前后用 maps 量。
- 已实现：判断推广到所有类型，按类型编号记在 `Ctx.tboxed`（`boxed_types`）；结构体、按值的枚举和 `T?` 一起按包含关系排序定义。`T?` 的访问集中在 `box_has`、`box_val`、`opt_none`、`opt_take` 四个函数里。`()?` 没有值可放，仍用指针。

## 9 已定

1. 不设大小上限：所有不递归的枚举都按值存放。
2. 先做枚举（第 7 节），再做 T?（第 8 节），每一轮前后都用 make bench 量。

# 设计：stage 4，spawn 改成任务（协程）加调度器

状态：做完了（第 10 节是结果和遗留）。

## 1 为什么做

lredis 用 16 条一批的流水线时只有真 Redis 的六分之一（约 21 万 / 120–139 万 req/s）。`T!` 改成按值存放以后，llua 快了 4–6 倍，lredis 却基本没动，所以分配不是 lredis 的瓶颈。剩下的头号嫌疑是线程交接：每条命令要

1. 连接线程 `send`：拿通道的锁，`pthread_cond_broadcast`，再拿全局的 `lk_sel_mu` 广播一次；
2. 数据库线程从 `pthread_cond_wait` 里醒来（要经过内核调度），执行，`send` 回复，又是两次广播；
3. 连接线程从 `recv` 里醒来。

一条命令两次跨线程唤醒，每次在 macOS 上要几微秒，正好对得上每条命令约 5 微秒的上限。另外 `lk_sel_mu` 是全局的：任何通道有新值，所有正在 `select` 的线程都会被叫醒。连接一多，这一项也会越来越贵。

一个连接一个线程还有别的问题：每个线程 8MB 栈、创建要几十微秒，几千个连接以后就撑不住了。

## 2 对语言没有可见的变化

`scope`、`spawn`、`Chan`、`select`、`after`、`std/net`、`time.sleep` 的写法和规则都不变，现有程序不用改。变的是 spawn 出来的东西：以前是一个系统线程，以后是一个**任务**（有自己的栈的协程），由运行时的调度器放到少数几个系统线程（**工作线程**）上运行。

可以看到的变化只有下面这些，都写进 DESIGN.md 第 15 节：

- 环境变量 `LARK_PROCS` 设定工作线程数，默认是 CPU 核数。`LARK_PROCS=1` 时所有任务都在一个系统线程上轮流运行。
- 任务只在“会等待”的地方让出：通道的 `recv` / `select`、`scope` 块尾、`time.sleep`，以及 `std/net` 的读、写、accept、connect。一直在算、不等待的任务会一直占着它的工作线程（不抢占）。别的工作线程照常运行。
- 文件读写、`os.run`、标准输入、`extern "c"` 函数这些会阻塞的调用，在等待时占住一个工作线程。如果所有工作线程都被这样占住，别的任务只能等着。

为什么不做 async/await：要改编译器，把函数拆成状态机，还要把函数分成两种颜色（async 的只能在 async 里调用）。语言会变复杂，现有代码也都要改。有栈的协程只改运行时，生成的 C 代码不用变。代价是每个任务一块栈（见第 5 节）。

## 3 调度器

M:N：多个任务放在 `LARK_PROCS` 个工作线程上。

- **第一次进入 `scope` 时才启动调度器。** 没有用到并发的程序（比如编译器自己）不创建任何东西，速度不变。启动时当前的系统线程成为 0 号工作线程，正在运行的代码成为“主任务”，继续用原来的栈；再创建其余的工作线程。
- **运行队列**：一个全局队列，用一把锁保护；每个工作线程另有一个“下一个”位置（Go 叫 `runnext`）。
  - 任务 A 唤醒任务 B 时（比如往 B 等着的通道 `send`），B 放进 A 所在工作线程的“下一个”位置。A 让出时，这个工作线程接着运行 B，不经过队列，也不用叫醒别的系统线程。
  - lredis 的连接任务和数据库任务就这样在同一个工作线程上来回交接，一次交接只是一次栈切换，大约几十纳秒。**这是这次改动要拿到的主要收益。**
  - “下一个”位置被占着时，原来的那个挪到全局队列，并叫醒一个空闲的工作线程。
  - 先不做工作窃取（work stealing）。等测出全局队列的锁是瓶颈再说。
- **空闲的工作线程**：没有任务时，一个工作线程负责等网络事件和定时器（见第 6 节），其余的睡在条件变量上。别的线程往队列里放任务时，按需叫醒一个睡着的线程，或者叫醒正在等网络事件的那个。
- 忙着的工作线程每调度 61 次就不等待地查一次网络事件（Go 的做法），所以一直有任务可运行时，网络事件也不会被饿着。

## 4 任务的生命周期

- `spawn(f, x)`：从栈池取一块栈，在上面准备好 `f(x)` 的入口，放进运行队列（不立刻运行，spawn 的一方继续）。
- `scope` 块对应的 `lk_scope` 里记着还没结束的任务数和正在等待的任务。块尾 `lk_scope_end`：计数不是 0 就把自己挂起，最后一个任务结束时把它叫醒。
- 任务结束时，栈还回栈池。
- panic 仍然让整个进程退出，调用栈信息是 panic 的那个任务的。
- `main` 返回时进程退出（结构化并发保证这时已经没有别的任务了）。

## 5 栈

- 每个任务的栈用 `mmap` 保留 **1MB**，最下面一页设成不可访问（保护页）。只有用到的页才占内存：一个只用了几 KB 栈的连接任务，实际只占几 KB。
- 现在线程栈是 8MB，是因为“递归较深的代码”。1MB 够 llua 这类递归到 200 层的解释器吗？要实测。不够就改成 8MB：保留的地址空间大一些，但实际占用的内存不变（1 万个任务也只是 80GB 地址空间）。
- 栈溢出碰到保护页会收到 SIGSEGV。先装一个用备用信号栈的处理函数，打印“任务的栈用完了”和调用栈后退出，不让它看起来像普通的崩溃。
- 结束的任务的栈放回池里，最多留 64 块，其余 `munmap`。

## 6 等待的实现

### 6.1 栈切换

`lk_swap(from, to)`：保存被调用者保存的寄存器和栈指针，换成另一个任务的。arm64（包括 d8–d15）和 x86_64 各写一段几十行的汇编，放在 `lark_rt.h` 里；其他平台用 `ucontext` 兜底（它每次切换要一次系统调用，慢，但能用）。

调用栈信息那条链（`lk_frame`）每个任务一条：切换时把工作线程上的链头存进任务，再换上要运行的任务的链头。

### 6.2 通道

- 去掉条件变量和全局的 `lk_sel_mu`。每个通道有一个等待者队列，等待者是“哪个任务、值放到哪里”。
- `send`：有等待者时，直接把值放到它给的位置，把它放进当前工作线程的“下一个”位置；没有就放进缓冲区。
- `recv`：缓冲区有值就取；否则如果除自己以外的持有者都放手了，返回 `None`；否则把自己登记成等待者，挂起。
- 放手（`lk_chan_release`）时叫醒这个通道的所有等待者，让它们重新检查是不是“都结束了”。
- `select`：在每个通道上都登记同一个等待者，再挂起。等待者里有一个原子的状态，第一个把它从“等待”改成“已完成”的 `send` 赢，别的通道看到“已完成”就跳过它；醒来后从其余通道上把自己摘掉。`after` 是在定时器堆里登记同一个等待者。
- 不同工作线程上的任务可能同时操作同一个通道，所以每个通道还是有一把锁，但锁只保护几行代码，不会在锁里睡眠。

### 6.3 网络

- 调度器启动以后，读、写、accept 先直接试（`MSG_DONTWAIT`；Listener 设成非阻塞），得到 `EAGAIN` 时挂起，等事件循环（macOS 用 kqueue，Linux 用 epoll）叫醒，再重试。
- fd 第一次要等某个方向时在事件循环里登记一次，用边沿触发（`EV_CLEAR` / `EPOLLET`），以后一直留着，关闭时系统去掉。事件来时没人在等，就在 fd 表里记一个“已就绪”，下一个要等的人看到它就不挂起。所以等待之前一定要先试过读写。
- fd 表按 fd 下标，不加锁（每页 1024 项，各项原子地读写）。关闭 socket 必须经过 `try_fd_close`，它清掉这一项的登记，因为 fd 的号码会被重用；用 `extern "c"` 自己关 socket 的话，这个号码以后的等待会卡住。
- `set_timeout`：运行时自己记截止时间，等待时同时在定时器堆里登记，先到的那个赢。
- 没有启动调度器时（没有用并发），网络函数照旧直接阻塞，不经过事件循环。

### 6.4 定时器

每个工作线程一个最小堆，各有一把锁。每个任务最多在一个堆里有一项：第一次设时放进当时所在线程的堆，以后原地改。线程平时只看自己的堆，每调度 61 次和当看守时看所有的。负责等网络事件的那个工作线程，等待的超时是所有堆里最近的到期时间。`time.sleep`、`select` 的 `after`、读写超时都用它。

## 7 引用计数

规则不变：有活着的任务时（`lk_nthreads` 不是 0）引用计数用原子操作。以后可以改进成“只有一个工作线程时也用普通加减”，但 `LARK_PROCS=1` 不是默认值，先不做。

## 8 分几步做

1. **栈切换、栈池、调度器、通道、`select`、`scope`、定时器。** 网络先不改，所以这一步只跑不用网络的例子（`examples/scope`、`select`、`strthreads`、`tail` 等），并且 `LARK_PROCS` 要大于同时阻塞的任务数。
2. **事件循环和非阻塞的网络。** `examples/net` 和 lredis 的测试通过以后，测 lredis。
3. **按测出来的结果调优。** 比如全局队列的锁、`LARK_PROCS=1` 的引用计数。
4. 把规则并进 DESIGN.md 第 15 节，README 写上 `LARK_PROCS`。

每一步都要过 `make test1` 和 `make bootstrap`。生成的 C 代码不变，所以种子不用更新。

## 9 怎样算做成了

| 测量 | 改之前（线程） | 改之后 | 目标 |
|---|---|---|---|
| 两个任务通过两个通道来回传一个数，一次来回 | 3530 | 189（第一步 175） | 1 微秒以内 |
| 4 个任务往一个通道里发，主任务收，每条消息 | 79 | 43（第一步 48） | 比改之前快 |

## 10 结果和遗留

stage 4 到此收尾。和设计相比，做的时候改了这些：

- 定时器、fd 表、运行队列各用各的锁，每个工作线程有自己的队列，空闲的去偷（原来打算先不做偷任务）。原因是采样：只有一把调度器锁时，lredis 大半时间花在线程抢锁和互相唤醒上，线程越多越慢（默认 14 万 req/s，1 个线程反而 47 万）。拆开以后默认是 34 万–35 万。
- 同一时间只叫醒一个空闲线程；每个任务在定时器堆里最多占一个位置。
- 采样分析用 `tools/sample-callers.awk`：从 `/usr/bin/sample` 的调用图里找出等锁、唤醒是哪个运行时函数发起的。

之后写 lhttp（`apps/lhttp`，静态文件 HTTP 服务器，50 个连接，每次读都带 30 秒的空闲超时）时又按采样改了几轮。用 `wrk -t4 -c50` 测，`ab` 只用一个线程，自己就是上限，几次之间相差 30%：

| 改动 | wrk req/s | 采样里最大的等待 |
|---|---|---|
| 起点（fd 表一把锁，定时器锁从挂起前拿到 kevent 之后） | — （ab -k 7.5 万–9.9 万） | fd_wait 里等定时器锁 1084 |
| 定时器锁只包住设定时器和登记等待者 | 10.6 万–11.0 万 | 每次等待一次 kevent，约 530 |
| fd 一直登记着，边沿触发 | 12.1 万–12.3 万 | 定时器锁 692 |
| 每个线程一个定时器堆 | 11.9 万–13.1 万 | 调度器的锁约 230，定时器锁约 100 |
| 文件缓存改成所有连接共用一个 `Mutex[T]`，解锁时直接交给排队的任务 | 7.3 万–7.5 万 | kevent 约 1070、cvsignal 约 170：一有冲突就每次都挂起、叫醒 |
| `Mutex` 改成解锁时只叫醒、让它重新抢，抢不到先空转 | 12.3 万–12.5 万（三轮几乎一样） | 调度器的锁约 190，`lk_mutex_lock` 里只有 20 |

最后一行里，进程大部分时间是空闲线程在等活干，忙着的时间主要花在 `recvfrom` / `sendto` 上：瓶颈已经不在运行时的锁上了。
`Mutex` 那两行的教训：锁直接交接给一个还没运行的任务，别的任务只能接着排队，形成“车队”，以后每次加锁都要经过调度器（Go 的 `sync.Mutex` 也是因此不交接）。

lcache（`apps/lcache`，键值缓存，数据分 16 段、每段一个 `Mutex`，用 lhttp 的 HTTP 模块）：`wrk -t4 -c50` 只读同一个键（50 个连接抢同一段）12.9 万–13.6 万 req/s，八成读两成写、散在 1000 个键上 12.3 万–13.4 万。采样里没有一次落在 `lk_mutex_lock` 上，和 lhttp 一样，时间在空闲和 `recvfrom` / `sendto` 上。

lgrep（`apps/lgrep`，grep，自带回溯的小正则引擎）：在 1.16 亿字节、约 300 万行的文件上，第一版 `fn [a-z_]+\(` 0.97 秒（BSD grep 0.74），`[0-9]+\.[0-9]+` 1.33 秒（grep 4.70），但 `-i err` 7.60 秒（grep 2.30）、找不存在的串 0.98 秒（grep 0.33）。查下来是语言的问题：`s += x` 生成的是 `s = lk_str_cat(s, x)`，每次新分配、整段复制，循环里拼字符串是平方的；`str.to_lower` 就是这样一个字节一个字节拼的。改成原地追加（`lk_str_append`，引用计数为 1 时不复制；`s += s` 时旧缓冲等复制完再释放），`to_lower` / `to_upper` 改在 `[u8]` 上改、只分配一次。lgrep 自己：整段只转一次小写、每行按位置匹配不再切出来，加了“能以哪些字节开头”的表跳过不可能的位置。改完以后（`make bench-grep`，各取 3 次里最短）：`fn [a-z_]+\(` 0.31 秒（grep 0.78），`-i err` 0.44（2.38），找不存在的串 0.27（0.35），`[0-9]+\.[0-9]+` 0.31（4.79），`^pub fn` 0.28（0.40），`-v ^ *$` 0.38（0.87），`TODO|FIXME|lk_[a-z]+_lock` 0.36（2.72）：七项都比 macOS 自带的 BSD grep 快，最慢的一项也只用了它 77% 的时间。

ledit（`apps/ledit`，终端文本编辑器）：写的时候碰到的语言问题，还没修，按痛的程度排：
- ~~列表没有在中间插入、删除~~：已加内置函数 `xs.insert_at(i, x)`、`xs.remove_at(i)`（`memmove` 整段挪），ledit 的 `insert_at` / `remove_at` 删掉了。
- ~~`&x` 传进去时其它参数里不能再出现 x~~：记错了。编译器早就是两阶段借用（`own.lark` 的 `aliases`）：其它参数先求值，只要不是指向 x 内部、非平凡类型的位置就允许，`edit(&ed, Ins(ed.row, ed.col, s))` 本来就能编译。写 ledit 时没试就先绕开了，现在改回直接写。
- `extern "c"` 不能传结构体和指针，调不了 `tcsetattr` / `ioctl(TIOCGWINSZ)`，只好调外部的 `stty`；也收不到信号（SIGWINCH 改窗口大小只能每秒查一次）；~~程序 panic 时没有地方恢复终端~~：`std/term` 进入原始模式时就用 C 的 atexit 登记了恢复终端；语言也有了 `defer` 和 `os.at_exit`（`examples/defer.lark`）。
- ~~`pop` 在空列表上 panic、没有返回 `T?` 的版本~~：已加 `xs.try_pop() -> T?`。那条报错也改了：列出能 match 的类型，scrut 是 pop 时提示用 try_pop（`tests/err1/match_pop`）。
- 结构体只要有一个字段不是 pub，模块外面连 pub 字段也不能改（报错说得清楚）：主程序改窗口大小得让 editor 模块提供 `resize`。规则是为了保住不变式，但对“大部分字段公开、少数内部”的状态结构体很别扭。
- ~~字符串没有 `\x1b` / `\e` 转义~~：已支持 `\e` 和 `\xHH`（正好两位十六进制，不对时报错）。
- ~~`fmt.width` 把所有三字节字符都算两列~~：改成按码点和东亚宽度表的主要区间算（`examples/width.lark`），ledit 的状态栏可以用回破折号了。

还没做的：

- **lredis 流水线没到 60 万。** 线程多了仍然比 1–2 个线程慢一些（35 万对 45 万–51 万）。剩下的大概是两件事，都还没验证：只有一个数据库任务，它跟着连接在线程之间跳；每条命令交接两次。下一步可以试 lredis 一次发一批命令，看交接次数是不是上限；调度器这边可以试空闲线程先空转一会儿再睡、让任务尽量回到上次运行的线程。
- spawn 约 2.8 微秒，没到 2 微秒的目标：一次 spawn 很多任务时，栈池（64 块）不够，要新 `mmap`。
- 栈用完时只是段错误退出，没有“任务的栈用完了”的报错（第 5 节设想的信号处理函数没有做）。
- `net.connect` 仍然阻塞；文件、管道、终端的读写也是。
- 只支持 arm64 和 x86_64，macOS（kqueue）和 Linux（epoll）。Linux 那部分还没有在 Linux 上编译、运行过，边沿触发的 epoll 也一样。
- `make bench`（不用并发的程序）前后测过，没有变慢（第 9 节）。
